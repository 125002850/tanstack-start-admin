00一句话总结

这套实现把后台系统做成了浏览器式多标签工作台:URL 是唯一真相, 标签栏只是"遥控器";页面实例统一托管在一个 ActivityHost 里做 keep-alive; 最难的活是切标签前驱逐上一页的弹窗/下拉等浮层,为此专门造了一台 "浮层驱逐机"。整体是一个防御性很强、测试密度很高、注释在解释"为什么"的工程级实现, 主要扣分点在于浮层驱逐依赖 DOM 选择器契约、手写路由匹配器这两处"走钢丝"的设计, —— 好消息是作者自己在性能评审文档里也承认了,并排好了整改路线。

02架构总览

数据永远单向流动:路由变化 → 同步器开/激活标签 → Store 更新 → 标签栏和 Viewport 各自消费。没有任何一处"标签栏直接改内容、路由再跟着改"的双向同步。

03实现思路,用大白话讲

① 为什么 URL 是唯一真相?

传统的标签页方案是"标签栏自己管一份页面列表,路由再管一份",两处状态互相追赶,极其容易出 bug。 这里反过来:标签栏里根本没有自己的页面列表逻辑——点一个标签就是 navigate(那个标签的 href), 路由变化后 useDashboardRouteTagSync 用 openOrActivate 把它激活。 副作用是:刷新页面后标签自然重建、URL 与标签永远一致、浏览器前进后退也自动正确。

② 页面实例为什么托管在 Viewport?

每个业务路由组件(如 dept.tsx)只做一件事:把"怎么渲染我"告诉注册中心,然后自己不渲染任何内容。 WorkspaceViewport 是唯一的"页面对外出租窗口":当前页正常展示,勾选了保活的旧页面用 <Activity mode="hidden"> 藏起来——DOM 和组件 state(表格筛选、表单草稿)都留着, 只是 Effect 被卸载。切回去就是显示回来,不用重新加载。 路由组件里那段 if (!isCurrentRouteInstance) return null 保证同一时刻只有一个路由在做注册,不会抢。

③ 最难的问题:切标签时,上一页的浮层怎么办?

Radix 的弹窗、下拉、抽屉都是 portal 到 document.body 的。你把页面 A 藏起来切到页面 B, A 打开着的下拉菜单不会跟着消失——它会悬浮在页面 B 之上。这就是 page-overlays.ts 存在的全部意义, 它做的事分四步:

  • 快照(timing 是关键):在标签的 pointerdown 时刻扫描"当前有哪些浮层开着"并存下来。 必须在 pointerdown 而不是 click 做——因为 Radix 会在 click 之前、通过"点击外部"的 pointerdown 先把非模态浮层标记为 closed(只剩退出动画),click 时再扫就晚了。
  • 关闭:对存下来的浮层派发合成的 Esc 键;如果 Esc 不管用,按优先级逐级升级: 找浮层里的显式关闭按钮点它 → 找控制它的 trigger 再点一次。 对 hover 型浮层(tooltip/popover)派发 pointerleave/mouseleave (不冒泡的事件 React 代理收不到,所以直接派发到元素上——代码注释里写明了这个坑)。
  • 等退出动画:挂一个 MutationObserver 盯 aria-expanded / data-state / data-open 的变化, 每帧检查"全关干净没有",没干净就每 40ms 重试一轮关闭,最多 8 次。
  • 超时兜底:500ms 还没干净就当它干净了,直接切换——用户永远不用等一个弹窗慢慢退场。
竞态防护:用户狂点标签怎么办?每次操作领一个递增的"号码牌"(sequence)。 等浮层退场完成后,发现自己手里的号码牌已经不是最新的,就放弃提交——最后一次点击说了算。

④ 保活页太多会吃光内存,怎么办?

保活标签有上限(MAX_KEEPALIVE_TABS = 15),超了按最久没访问的驱逐。 两个细节很讲究:驱逐逻辑放在和"打开标签"同一个原子 set() 里执行 (注释记载:以前是 set 外补刀,引发了订阅顺序 bug);并且绝不驱逐脏页面和刚打开的页面 (刚打开的页面生命周期快照还没注册,可能被误判为可驱逐)。

⑤ 脏标记与关不掉的门

每个页面可以通过 useWorkspacePage() 拿到一个生命周期通道,报告"我有未保存的更改"和 "关我之前先问我"(closeGuard)。关标签、关其他、关全部之前都会先过这道门, 1.5 秒不回答就当拒绝处理并 toast 提示。脏标签在标签栏上显示一个小圆点。 —— 目前这部分是"先铺好管道",生产页面还没接入。

⑥ 一个页面崩溃了会怎样?

每个标签槽有自己的错误边界:崩溃时显示兜底卡片(DEV 环境还会提示先跑 pnpm api && pnpm typecheck), 同时自动禁用该标签的 keep-alive。效果是:切走时它被真正卸载,切回来重新挂载——崩溃的页面自愈了。

⑦ 性能上的小心思

  • render 闭包缓存:切换可见性只改 activeId,Viewport 不会重新执行所有保活页的 render()。
  • Context 拆分:active 和 { tabId, updateLifecycle } 分成两个 Context, 只关心生命周期的页面不会因为显隐而整页重渲染。
  • renderKey:同页 URL 查询参数变化时(如 ?page=2),以路径+search 为 key 刷新 descriptor, 组件树原地更新、局部 state 保留。

04点击一个标签,背后发生了什么

  1. pointerdown(比 click 更早) TagsBar 的 prepareActivate 抢在 Radix 把非模态浮层标为 closed 之前,扫描当前页面的浮层并快照。
  2. click → openOrActivate(tab, snapshot) 拿快照派发合成事件关掉上一页所有浮层。没有浮层?跳过等待,直接走第 4 步。
  3. 等浮层退场 MutationObserver + 40ms 重试 + 500ms 超时。期间用户又点了别的标签?号码牌作废,本次操作放弃。
  4. navigate(tab.href) 改 URL。此刻标签栏状态还没动。
  5. 路由变化 → useDashboardRouteTagSync 苏醒 匹配最深路由,解析标题/keepAlive/closable,调用 store 的 openOrActivate(已存在 → 只更新激活与最近访问时间)。
  6. store 原子提交 activeId 切换 + lastVisitedAt 刷新 + 超限时同帧 LRU 驱逐。store 内再补一刀:对上一个 activeId 兜底驱逐浮层(双保险)。
  7. 两个消费者各自响应 TagsBar 重新着色高亮;Viewport 把新页面的 Activity 切 visible、旧页面切 hidden(保活)或卸载(不保活)。
  8. 新页面的 Boundary 注册 descriptor layout effect 里把 render 闭包写进 registry——下一次切换时它才渲染。若 renderKey 变了(URL 参数不同),刷新 descriptor。
为什么要在 store 和 Viewport 两处都驱逐浮层?因为切标签有两个入口:点标签(hook 路线,有快照) 和直接导航/键盘/侧栏(store 路线,无快照,退化为全局扫描)。两处互为兜底,宁可多关不可漏关。

06风险与扣分点

级别问题说明
P1 结构债 浮层驱逐靠 DOM 契约 几十个 [data-slot][data-state] 选择器 + 合成事件模拟,依赖 Radix 内部实现。Radix/Base UI 一升级就可能全盘失效;document 级扫描还可能误伤不属于当前页面的全局浮层;退出动画只能靠轮询+超时,无法表达真实完成时机。作者的整改方向(显式 overlay registry + Portal 容器)是对的。
P2 手写路由匹配器 compileRoutePattern 手写 $param → [^/]+ 的正则编译器,加 routesByPath as unknown as Record<string, unknown> 的类型逃逸,重造了 TanStack Router 的匹配轮子。路由语法演进时这里不会跟着走。
P1 Activity 生命周期契约未强制 hidden 状态下页面 Effect 会被清理,业务页必须容忍反复 mount/cleanup;但没有任何契约测试或 StrictMode 覆盖来抓"假设 Effect 隐藏时还在跑"的页面(定时器、轮询、WebSocket、音频)。
P2 lifecycle 通道暂无消费者 dirty / closeGuard / updateLifecycle 全线铺好但生产页面未接入;"未保存拦截"目前是纸面能力。evictInactive 无调用方,且不检查 dirty/closeGuard——未来一旦有人调用,可能静默丢掉有未保存更改的标签。
P2 openOrActivate 双实现 store 版(立即提交)与 hook 版(等浮层退场再导航)逻辑相似,各自维护一套 sequence。目前注释清晰、测试覆盖,但两处要同步理解。
备忘 性能无实测基线 render 缓存、Context 拆分等优化思路正确,但切换耗时/内存基线还没建。拖拽排序也只改视觉顺序,不持久化——属于产品取舍,不算缺陷。
